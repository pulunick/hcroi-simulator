## 1. 지금 가진 것 (자산)

main 브랜치에 이미 있는 것이 상용 제품의 **코어**다. 다시 만들지 않는다.

- 계산 엔진(`src/lib/hcroi/`): HCROI/HCVA 수식, 시나리오 A/B, 손익분기 역산, 규칙 기반 인사이트, 기간 레코드(연·반기·분기·월)와 합산
- 입출력: 엑셀 내보내기/템플릿/가져오기(미리보기·되돌리기), **결산서 PDF 가져오기**(브라우저 안 pdf.js, 서버 없음)
- 화면 4개(대시보드·시뮬레이터·데이터 관리·가이드), 인라인 SVG 차트, 반응형
- 테스트 144건, 사용 설명서, 스펙 문서
- 아키텍처가 이미 **서버 없는 로컬 계산**이라 추천안(§3)에 그대로 맞는다

없는 것: 다중 회사(작업공간) 전환, 로그인·결제·라이선스, 리포트 출력, 부서별·동종업계, 마케팅 페이지, 데스크톱 패키징.

## 2. 누구에게 무엇을 파는가

### 2.1 타깃 (지불 의사 순)

| 순위 | 세그먼트                                                        | 상황                                                                             | 필요한 것                                            |
| ---- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1    | **HR 컨설턴트 · 노무법인 · 회계법인 · 경영 컨설팅**             | 여러 고객사의 인건비 진단을 반복. 결산서를 받아 엑셀로 수작업                    | 회사별 작업공간, 브랜딩된 리포트, 동종업계 비교      |
| 2    | **중견·중소기업 인사팀장 / HRBP / 경영기획** (임직원 100~2,000) | 연 1~4회 인건비·정원 검토. 경영진에게 "인원 늘리면 이익이 어떻게 되나" 답해야 함 | 시뮬레이터, 경영진 보고 리포트, 결산서 PDF 자동 입력 |
| 3    | CFO · 경영진                                                    | 직접 쓰기보다 결과를 본다                                                        | 리포트 1장, 등급, 판단 문장                          |

1순위를 컨설턴트로 두는 이유: 한 사람이 여러 회사를 다루므로 "작업공간 여러 개"의 가치가 분명하고, 도구 비용을 고객에게 전가할 수 있어 가격 저항이 낮다. 사내 담당자(2순위)는 1명·1사라 단가가 낮지만 수가 많다.

### 2.2 해결하는 문제

1. 결산서(PDF)·급여 대장(엑셀)에서 숫자를 옮겨 적는 수작업
2. HCROI 를 계산은 하지만 **해석**을 못 한다 → 등급·판단 문장·개선 시나리오
3. "정원 10% 늘리면?" 을 물을 때마다 엑셀을 다시 짠다 → 시나리오 A/B 즉시 비교
4. 인건비 데이터를 외부 서버에 올리기 싫다 → 로컬 우선

### 2.3 대안(경쟁)

- 엑셀 수작업(가장 큰 경쟁자, 무료). 이길 방법: PDF 자동 입력 + 시나리오 + 리포트를 한 번에
- 대형 HRIS(SAP SuccessFactors, Workday 등)의 애널리틱스: 비싸고 HCROI 특화 아님, 중소기업은 못 쓴다
- 국내 HR SaaS(급여·근태 중심): HCROI/시뮬레이션 기능 없음. 향후 **연동 파트너** 후보이지 경쟁자는 아님
- 컨설팅 보고서: 1회성·고가. 우리는 "상시 도구"

## 3. 제공 형태 비교

| 기준                      | A. 유료 웹서비스(계정·DB SaaS)            | B. 로컬 우선 웹 + 라이선스 키 ★        | C. 설치형(데스크톱)                       | D. 소스·영구 라이선스 판매 |
| ------------------------- | ----------------------------------------- | -------------------------------------- | ----------------------------------------- | -------------------------- |
| 회사 데이터 보관          | 우리 서버(Supabase 등)                    | 사용자 브라우저·파일                   | 사용자 PC                                 | 고객 서버                  |
| 보안 심사·구매 장벽       | 높음(인건비 데이터 반출 승인 필요)        | 낮음("서버로 안 감"을 명시 가능)       | 낮음                                      | 낮음                       |
| 추가 개발량(현 코드 대비) | 큼: 인증·멀티테넌시·RLS·백업·마이그레이션 | 중: 작업공간·라이선스·결제 웹훅        | 중+: B 에 Tauri 패키징·서명·자동 업데이트 | 작음(문서·배포)            |
| 운영 부담(1인)            | 큼: 장애·보안·개인정보 책임               | 거의 없음(정적 호스팅 + 서버 함수 2개) | 설치 지원·OS 별 빌드                      | 버전별 지원                |
| 업데이트 배포             | 즉시                                      | 즉시(웹)                               | 자동 업데이트 구현 필요                   | 고객이 적용                |
| 사내망·오프라인           | 불가                                      | 부분(한 번 로드 후 오프라인 가능, PWA) | 가능                                      | 가능                       |
| 과금 방식                 | 월/연 구독, 좌석                          | 연 라이선스(키), 오프라인 검증 가능    | 영구 또는 연                              | 1회 고액                   |
| 확장(공유·협업)           | 쉬움                                      | 어려움(파일 주고받기)                  | 어려움                                    | —                          |
| 판단                      | **보류** — 협업 요구가 실제로 생기면 그때 | **1차 추천**                           | **2차** — B 위에 얹는다                   | 대기업·공공 요청 시 옵션   |

**B 를 고르는 이유 세 가지.** ① 현 아키텍처와 완전히 일치해 코어를 다시 쓰지 않는다. ② 인건비·결산 데이터는 회사에서 가장 민감한 축에 들고, 2026-09-03 실무 회신도 "개인 PC 저장 선호"였다. ③ 1인 개발자가 감당할 운영 범위다. 협업·공유 요구가 진짜로 나오면 그때 A 로 확장해도 코어는 그대로다.

## 4. 추천안 아키텍처 (B + C)

```
[사용자 브라우저 / Tauri 창]                      [Vercel]
  SvelteKit 정적 빌드 ─ 계산·차트·엑셀·PDF (지금과 동일)     ├ /api/license/verify   (선택: 온라인 재검증)
  작업공간 N개 ─ IndexedDB + .hcroi 파일 내보내기/열기        ├ /api/payment/webhook  (PG → 키 발급·메일)
  라이선스 키 ─ Ed25519 서명 토큰, 오프라인 검증               └ /api/peer            (동종업계, DART Open API 프록시 — 회사 데이터 안 보냄)
```

- **서버는 회사 데이터를 받지 않는다.** 서버 함수는 라이선스·결제·공개 API 프록시만. 개인정보처리방침이 단순해지고, 보안 질문지에 "데이터 미보관"으로 답한다
- **라이선스 키**: 발급 시 서명(만료일·티어·좌석·이메일 해시 포함). 클라이언트는 공개키로 검증 → 오프라인·사내망 OK. 온라인 재검증은 선택(취소·환불 대응)
- **작업공간**: `workspace.svelte.ts` 를 "작업공간 컬렉션"으로 확장. localStorage → IndexedDB(용량). 파일 형식은 기존 JSON 을 `.hcroi` 로 이름만 바꾸고 버전 필드 추가. 엑셀 왕복은 유지
- **설치형**: Tauri 2 로 같은 빌드를 감싼다. 파일 저장은 네이티브 다이얼로그, 자동 업데이트는 Tauri updater. Windows 코드 서명 인증서 비용 발생(§8)
- **하지 않는 것**: 계정 시스템, DB, 서버 사이드 렌더링. `supabase/` 는 계속 손대지 않는다(brain §9)

## 7. UI/UX 방향 (Claude Design 으로 진행)

### 7.1 원칙

1. **숫자를 넣으면 판단이 나온다.** 모든 결과 화면의 첫 줄은 수치가 아니라 문장("인건비 1원당 1.35원을 벌고 있습니다 — 보통 등급")
2. **3단계 이내에 첫 결과.** 회사 이름 → 데이터(엑셀 / PDF / 직접 입력 중 택일) → 대시보드
3. **전문 용어는 항상 풀이와 함께.** HCROI·HCVA 는 툴팁이 아니라 옆에 한 줄 설명
4. **데이터가 어디 있는지 항상 보인다.** 상단에 "이 PC 에만 저장됨 · 마지막 저장 3분 전 · 파일로 내보내기"
5. 기존 규칙 유지: 단위 명시(원·%·명·배), 이중축 금지, 범주형 색 고정, 표 병행
6. 경영진 리포트는 **인쇄를 전제**로 흑백에서도 읽히게

### 7.3 진행 방식

1. 이 문서 §10 결정 후, Claude Design 캔버스로 **랜딩 · 홈 · 온보딩 · 대시보드 · 리포트** 5개 아트보드 초안
2. 캔버스에서 사용자가 직접 손보고, 확정본을 코드로 옮긴다(디자인 토큰은 현 Tailwind `brand/ink/line/surface` 를 확장)
3. 시뮬레이터·데이터 화면은 기존 코드 기반으로 정리만

## 9. 사내 버전(main)과의 관계 — 브랜치 전략

상세는 [branch-strategy.md](branch-strategy.md). 요지:

- **main** 은 인사담당자 사내 도구로 계속 진행(수정·개선 요청은 전부 main). **product/commercial** 은 판매용
- 머지는 **main → product 한 방향만**. 계산 엔진·엑셀·PDF(`src/lib/hcroi/**`)는 main 에서만 고치고 상용 브랜치는 쓰기만 한다 → 코어는 충돌 없이 흘러온다
- 상용 브랜치에만 있는 것: 작업공간 컬렉션, 라이선스, 리포트, 마케팅, 설치형 — 전부 새 디렉터리·새 경로
- `.claude/state.md` 는 브랜치별로 따로(`merge=ours`)
- 저장소 분리(§8-1) 결정 뒤 private 저장소가 public 을 `core` 리모트로 두고 같은 방식으로 머지. 그 전까지는 이 브랜치에 **문서와 디자인만** 쌓고 결제·라이선스 코드는 넣지 않는다

## 10. 결정이 필요한 것 (답을 주면 brain.md 로 옮긴다)

1. **형태**: 추천안(로컬 우선 웹 + 라이선스 → 설치형)으로 갈 것인가, 아니면 처음부터 계정형 SaaS 인가
2. **저장소**: private 전환 / 새 private 레포 / open-core 중 무엇
3. **1순위 타깃**: 컨설턴트(다사) vs 사내 인사담당자(1사)
4. **결제 시작 방식**: 수동 견적·이체로 시작 vs PG 부터
5. **제품명** (한글·영문). "Martin" 은 쓰지 않는다는 전제
6. **권리 관계 확인 여부**: 회사·지침 저자와 정리했는가, 필요 없는 상황인가
7. **첫 디자인 범위**: §7.3 의 5개 아트보드로 시작해도 되는가
