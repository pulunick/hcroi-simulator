## 1. 지금 가진 것 (자산)

main 브랜치에 이미 있는 것이 상용 제품의 **코어**다. 다시 만들지 않는다.

- 계산 엔진(`src/lib/hcroi/`): HCROI/HCVA 수식, 시나리오 A/B, 손익분기 역산, 규칙 기반 인사이트, 기간 레코드(연·반기·분기·월)와 합산
- 입출력: 엑셀 내보내기/템플릿/가져오기(미리보기·되돌리기), **결산서 PDF 가져오기**(브라우저 안 pdf.js, 서버 없음)
- 화면 4개(대시보드·시뮬레이터·데이터 관리·가이드), 인라인 SVG 차트, 반응형
- 테스트 144건, 사용 설명서, 스펙 문서
- 아키텍처가 이미 **서버 없는 로컬 계산**이라 추천안(§3)에 그대로 맞는다

없는 것: 다중 회사(작업공간) 전환, 로그인·결제·라이선스, 리포트 출력, 부서별·동종업계, 마케팅 페이지, 데스크톱 패키징.

## 2. 누구에게 무엇을 파는가

### 2.1 타깃 (지불 의사 순)

| 순위 | 세그먼트                                                        | 상황                                                                             | 필요한 것                                            |
| ---- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1    | **HR 컨설턴트 · 노무법인 · 회계법인 · 경영 컨설팅**             | 여러 고객사의 인건비 진단을 반복. 결산서를 받아 엑셀로 수작업                    | 회사별 작업공간, 브랜딩된 리포트, 동종업계 비교      |
| 2    | **중견·중소기업 인사팀장 / HRBP / 경영기획** (임직원 100~2,000) | 연 1~4회 인건비·정원 검토. 경영진에게 "인원 늘리면 이익이 어떻게 되나" 답해야 함 | 시뮬레이터, 경영진 보고 리포트, 결산서 PDF 자동 입력 |
| 3    | CFO · 경영진                                                    | 직접 쓰기보다 결과를 본다                                                        | 리포트 1장, 등급, 판단 문장                          |

1순위를 컨설턴트로 두는 이유: 한 사람이 여러 회사를 다루므로 "작업공간 여러 개"의 가치가 분명하고, 도구 비용을 고객에게 전가할 수 있어 가격 저항이 낮다. 사내 담당자(2순위)는 1명·1사라 단가가 낮지만 수가 많다.

### 2.2 해결하는 문제

1. 결산서(PDF)·급여 대장(엑셀)에서 숫자를 옮겨 적는 수작업
2. HCROI 를 계산은 하지만 **해석**을 못 한다 → 등급·판단 문장·개선 시나리오
3. "정원 10% 늘리면?" 을 물을 때마다 엑셀을 다시 짠다 → 시나리오 A/B 즉시 비교
4. 인건비 데이터를 외부 서버에 올리기 싫다 → 로컬 우선

### 2.3 대안(경쟁)

- 엑셀 수작업(가장 큰 경쟁자, 무료). 이길 방법: PDF 자동 입력 + 시나리오 + 리포트를 한 번에
- 대형 HRIS(SAP SuccessFactors, Workday 등)의 애널리틱스: 비싸고 HCROI 특화 아님, 중소기업은 못 쓴다
- 국내 HR SaaS(급여·근태 중심): HCROI/시뮬레이션 기능 없음. 향후 **연동 파트너** 후보이지 경쟁자는 아님
- 컨설팅 보고서: 1회성·고가. 우리는 "상시 도구"

**B 를 고르는 이유 세 가지.** ① 현 아키텍처와 완전히 일치해 코어를 다시 쓰지 않는다. ② 인건비·결산 데이터는 회사에서 가장 민감한 축에 들고, 2026-09-03 실무 회신도 "개인 PC 저장 선호"였다. ③ 1인 개발자가 감당할 운영 범위다. 협업·공유 요구가 진짜로 나오면 그때 A 로 확장해도 코어는 그대로다.

## 4. 추천안 아키텍처 (B + C)

```
[사용자 브라우저 / Tauri 창]                      [Vercel]
  SvelteKit 정적 빌드 ─ 계산·차트·엑셀·PDF (지금과 동일)     ├ /api/license/verify   (선택: 온라인 재검증)
  작업공간 N개 ─ IndexedDB + .hcroi 파일 내보내기/열기        ├ /api/payment/webhook  (PG → 키 발급·메일)
  라이선스 키 ─ Ed25519 서명 토큰, 오프라인 검증               └ /api/peer            (동종업계, DART Open API 프록시 — 회사 데이터 안 보냄)
```

- **서버는 회사 데이터를 받지 않는다.** 서버 함수는 라이선스·결제·공개 API 프록시만. 개인정보처리방침이 단순해지고, 보안 질문지에 "데이터 미보관"으로 답한다
- **라이선스 키**: 발급 시 서명(만료일·티어·좌석·이메일 해시 포함). 클라이언트는 공개키로 검증 → 오프라인·사내망 OK. 온라인 재검증은 선택(취소·환불 대응)
- **작업공간**: `workspace.svelte.ts` 를 "작업공간 컬렉션"으로 확장. localStorage → IndexedDB(용량). 파일 형식은 기존 JSON 을 `.hcroi` 로 이름만 바꾸고 버전 필드 추가. 엑셀 왕복은 유지
- **설치형**: Tauri 2 로 같은 빌드를 감싼다. 파일 저장은 네이티브 다이얼로그, 자동 업데이트는 Tauri updater. Windows 코드 서명 인증서 비용 발생(§8)
- **하지 않는 것**: 계정 시스템, DB, 서버 사이드 렌더링. `supabase/` 는 계속 손대지 않는다(brain §9)

## 7. UI/UX 방향 (Claude Design 으로 진행)

### 7.1 원칙

1. **숫자를 넣으면 판단이 나온다.** 모든 결과 화면의 첫 줄은 수치가 아니라 문장("인건비 1원당 1.35원을 벌고 있습니다 — 보통 등급")
2. **3단계 이내에 첫 결과.** 회사 이름 → 데이터(엑셀 / PDF / 직접 입력 중 택일) → 대시보드
3. **전문 용어는 항상 풀이와 함께.** HCROI·HCVA 는 툴팁이 아니라 옆에 한 줄 설명
4. **데이터가 어디 있는지 항상 보인다.** 상단에 "이 PC 에만 저장됨 · 마지막 저장 3분 전 · 파일로 내보내기"

| 기준               | H1 무료 + 서비스 | H2 결과물 과금    | H3 파트너 라이선스 |

| 첫 매출까지        | 빠름(1건 대행)   | 느림(8주+)        | 가장 느림(영업)    |
| 권리·저장소 문제   | 가장 가벼움      | 다시 생김         | 계약 전 필수 정리  |
| 개발자 본업과 충돌 | 큼               | 작음              | 중                 |

**추천: H1 → H2 순서로 검증하고, H3 는 접촉만 병행한다.**

1. 지금 도구를 그대로 무료 공개하고 문의 폼 하나만 붙인다(H1 실험). 돈 얘기 없이 **누가 무엇을 요청하는지**가 나온다 — 이것이 H2/H3 의 근거가 된다.
2. 요청에 "보고서" · "여러 회사"가 반복되면 그때 워터마크 리포트로 H2 를 시험한다. 계산 기능은 끝까지 잠그지 않는다(§5 원칙 유지).
3. 노무법인·컨설팅 지인 2~3곳에는 지금부터 데모 링크를 보낸다(H3 탐색). 반응이 오면 그쪽이 가장 큰 매출이 된다.

무료로 시작해도 잃는 것은 없다. 반대로 유료로 시작했다가 무료로 풀면 "안 팔려서 풀었다"가 된다. §10-1·4 (형태·결제 시작 방식) 답은 이 순서에 따라 "B 형태 · 결제 없이 시작" 으로 정리된다.

### 개정 (2026-09-14) — "누가 내는가"를 다시 좁힘

부업 조건(1인 · 본업 있음 · 시장 작음)으로 세 가설을 다시 재면 H1 은 **실험**으로는 맞지만 **수익 모델**로는 가장 비효율(시간 판매, 본업 충돌)이다. 돈을 낼 사람은 인사담당자가 아니라 **인사담당자를 고객으로 둔 사람**이고, 팔 것은 "여러 고객사 + 자기 로고 박힌 리포트" 라이선스다 — §2.1 이 이미 1순위로 꼽은 타깃인데 §11 에서 흐려졌던 것.

|                             | 첫 매출   | 시간당 수익                                  | 확장성 | 본업 충돌     |
| --------------------------- | --------- | -------------------------------------------- | ------ | ------------- |
| H1 대행·교육                | 빠름      | 최악(시간 판매)                              | 없음   | 큼            |
| H2 담당자에게 워터마크 제거 | 느림      | 낮음(단가 10–20만, 결재 필요, 연 1–4회 사용) | 중     | 작음          |

| H3 화이트라벨               | 가장 느림 | 높음                                         | 높음   | 중(영업·계약) |

컨설턴트가 맞는 이유: ① **매주 결산서를 받는 사람** — PDF → 숫자 자동 입력이 이 도구의 진짜 10배 기능인데 그 고통을 매주 겪는 사람만 돈을 낸다(담당자는 연 1–2회라 엑셀로 버틴다) ② **비용을 고객에게 청구** — 진단 한 건 수백만 원인 사람에게 연 100만 원 도구비는 결재 스트레스가 없다 ③ **로고 박힌 리포트**는 그들에겐 제품 자체라 워터마크 제거가 "쪼잔"하지 않다.

**개정된 순서**

1. 지금 배포본 + 랜딩 1장 + 문의 폼(M4 를 M1 앞으로). CTA 두 갈래: 담당자 무료 시작 / 컨설턴트 문의. 기다리지 않고 **노무법인·HR 컨설팅 10곳에 직접 링크 발송**(지인 2–3 + 콜드 7). 묻는 것 하나: "고객사 결산서 받아 이걸로 돌리고 로고 붙여 보고서 내는 데 연 얼마면 사겠나"
2. **2곳 이상이 "산다"고 하면** M1 다중 작업공간 + M3 리포트. 그 전엔 코드를 짜지 않는다. 첫 5건은 견적서·계좌이체·수동 키
3. 설치형(Tauri)은 대기업이 "사내망 아니면 못 쓴다"고 할 때만 — Cyberduck/Mountain Duck 구조의 2차 유료 제품(아래 보론)
4. H3 화이트라벨은 컨설턴트 고객 중 규모 큰 곳이 먼저 요구할 때 그 요구를 계약으로. 먼저 영업 다니지 않는다

하지 말 것: 인사담당자에게 뭔가를 잠그는 것(계산·시뮬레이터·PDF 는 끝까지 무료) · 첫 고객 전 라이선스·결제 코드 · H1 대행을 매출로 잡는 것(문의는 리드).

**솔직한 천장**: 컨설턴트 라이선스만으로는 대략 수십 곳 × 연 100만 원대 = **연 수천만 원**. 부업으로는 좋고 사업은 아니다. 그 이상은 H3 — 급여·HRIS SaaS 한 곳과 연동 계약 한 건이 위 전체를 넘는다. 그래서 "컨설턴트 라이선스로 현금과 레퍼런스 → 그걸 들고 SaaS 파트너" 순서.

**보론 — Cyberduck 류 무료 도구는 어떻게 버나(2026-09-14 사용자 질문)**: Cyberduck 은 GPL 무료 배포인데 수익은 ① 앱스토어 유료판(같은 소프트웨어, 자동 업데이트 값) ② 기부 키(기부 요청 창 해제) ③ **Mountain Duck**(별개 상용 제품, 영구 라이선스) — 사실상 무료 본체는 유입 채널이고 돈은 옆의 유료 제품이 번다. Sublime(양심 과금·모수로 버팀), WinRAR(법인 감사 리스크로 B2B 만 결제), Obsidian(앱 무료 + Sync/Publish 구독 + 상업 라이선스), 7-Zip/Notepad++(순수 기부, 수익 0)도 같은 결론: **무료 도구 자체로 버는 곳은 없고 "옆에 세운 유료 제품" 또는 "법인 결제 이유"가 있어야 한다.** 이 프로젝트에 기부·스토어 모델이 안 맞는 이유 셋 — 모수가 작다(한국 인사담당자), 사용 빈도가 낮다(결산 주기), 개인이 결제하지 않는다(회사 돈 = 견적서 세계). Mountain Duck 자리에 해당하는 것이 §3 의 설치형(Tauri) — "결산 데이터가 사내망을 벗어나지 않는다"가 법인이 돈 낼 명분. 반론: Tauri 패키징·서명·업데이트 채널 유지가 1인에게 만만치 않고 라이선스 키 발급이 필요해 "서버 없음" 장점이 일부 깎인다 → 컨설턴트 매출이 먼저.

**왜 웹(로컬 우선)인가 — 부업 조건**: 부업의 최대 적은 운영. 계정형 SaaS 는 "로그인이 안 된다"가 평일 오후 2시에 오고, 인건비 데이터를 내가 보관하는 책임이 생긴다. 로컬 우선 웹은 Vercel 정적 배포·서버 0·데이터 책임 0·코드 변경 0(지금 배포본 그대로). 컨설턴트에게 팔려면 M1 의 두 요소가 필수 — 작업공간 여러 개(IndexedDB) + `.hcroi` 파일 저장·열기(브라우저 데이터는 캐시 삭제·PC 교체로 날아가므로 파일이 백업이자 고객사 전달 수단이고, "데이터는 귀사 파일에만 있습니다"를 실제로 성립시킨다). 라이선스 확인은 서명된 키를 브라우저에서 검증(M2), 서버 불필요.

1. **허락을 문서로.** 담당자에게 메일 또는 메신저로 한 번 더 확인하고 캡처를 개인 보관. 담아야 할 문장 네 개 — ① 요구사항은 개인적 요청이었다 ② 도구를 상업적으로 배포·판매해도 된다 ③ 대가·지분은 없다(또는 있다면 무엇인지: 감사 표기 · 영구 무료 라이선스 등) ④ "Martin's HCROI Simulator 2.0" 지침 문서의 저작권자와 사용 범위(요구사항 참고용으로만 썼고 문서 자체는 배포하지 않는다). 이 문서는 저장소에 넣지 않는다.
2. **개인 프로젝트 위생.** 지금 지켜지고 있는 것: 개인 계정 저장소, 개인 커밋 주소, 실제 재무 수치·타사명 미커밋. 계속 지킬 것: 이 PC 의 gh 기본 계정이 다른 계정이므로 push 는 반드시 `pulunick` 으로 전환해서(brain §1 절차), 담당자가 시험용으로 쓰는 실제 결산서·수치는 담당자 PC 에만.
3. **제품명과 브랜드.** 담당자·"Martin" 과 무관한 이름. 도메인·상표 검색 후 확정(§10-5).
4. **첫 공개 = 무료(§11 H1).** 현재 main 그대로 배포하고 문의 폼 하나. 담당자에게도 같은 **공개 링크**를 준다.
5. **매출이 생기기 직전에** 개인사업자 등록(세금계산서·통신판매 여부는 그때 판단). 그 전에는 돈을 받지 않는다 — 무료 단계에서 필요 없는 일을 앞당기지 않는다.
6. **담당자와의 관계 정의.** 첫 사용자 · 요구사항 제공자 · 피드백 채널. 감사 표기 여부와 영구 무료를 약속하고 1번 문서에 같이 적는다. 공동 개발자·지분 관계는 아니다.

### 하지 않아도 되는 것

- 회사 관련 확인 일체 (승인·법무·규정 — 회사와 무관한 개인 프로젝트다)
- 저장소 private 전환 (§11 H1·H3 는 공개가 유리. H2 로 가서 결제 코드가 생길 때만 다시 판단)
- 결제·라이선스 코드 (§11 순서상 아직)
